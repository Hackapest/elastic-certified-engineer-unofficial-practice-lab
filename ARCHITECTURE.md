# Architecture

A self-contained lab for preparing for the **Elastic Certified Engineer** exam.
Clone the repo, run the installer, and you get two Elasticsearch clusters with
Kibana, sample data, a large catalog of exam-style tasks with automatic
checking, troubleshooting scenarios, and progress tracking.

## Goals

- One command to install, one to reset, one to uninstall.
- A large catalog of tasks across everything that can appear on the exam,
  mapped onto a full taxonomy of the curriculum (each query type, each ingest
  processor, etc.). There is no requirement that every taxonomy entry has a
  task.
- Grade tasks automatically by inspecting cluster state, as the real exam does.
- Track which parts of the curriculum the user has done and which remain.
- Minimal host dependencies: Docker, Docker Compose v2, Python 3.10+.

## Target version

Elasticsearch and Kibana **9.3.x**, pinned by a single `ES_VERSION` variable in
`.env`. Moving to a new exam version is a one-line change plus a selftest run.

## Repository layout

```
.
├── install.sh            # preflight, certs, compose up, license, sample data
├── uninstall.sh          # remove containers, volumes, images, certs
├── ece                   # the CLI (Python 3, standard library only)
├── .env                  # ES_VERSION, password, ports, heap size
├── compose.yaml          # at the root so plain `docker compose ps|logs` work
├── docker/
│   ├── Dockerfile        # official ES image + vim + lab scripts
│   ├── config/           # elasticsearch.yml per node
│   ├── instances.yml     # certificate subjects
│   ├── gen-certs.sh      # `certs` one-shot service
│   └── ece-entrypoint.sh # installs the node's config on first start
├── lib/                  # CLI internals: ES client, task engine, progress
├── taxonomy/             # the exam curriculum as a tree of feature IDs
├── tasks/                # task templates (Python), grouped by domain
└── scenarios/            # troubleshooting scenarios (break / verify / explain)
```

User state (progress, active task instances, active scenario) lives in
`.state/` (gitignored), outside Docker, so it survives resets.

## Infrastructure

### Topology

| Component  | Cluster A           | Cluster B           |
|------------|---------------------|---------------------|
| ES nodes   | `es-a1`, `es-a2`, `es-a3` | `es-b1`, `es-b2`, `es-b3` |
| ES port    | 9200 (via `es-a1`)  | 9201 (via `es-b1`)  |
| Kibana     | `kibana-a` on 5601  | `kibana-b` on 5602  |

- All nodes have the default roles (master-eligible, all data tiers, ingest,
  remote cluster client, ...). Tasks that need dedicated tiers change roles
  themselves, which is an exam topic in its own right.
- Nodes carry **custom attributes** for allocation filtering and awareness:

  | Node | `node.attr.zone` | `node.attr.temp` |
  |------|------------------|------------------|
  | x1   | zone-1           | hot              |
  | x2   | zone-2           | hot              |
  | x3   | zone-3           | warm             |
- Heap: 1 GB per node (configurable in `.env`), enough for the sample data.
- One fixed `elastic` password, set in `.env` and printed by `install.sh` and
  `./ece status`.

### Image

The official Elasticsearch image plus a thin layer that installs **vim**, so
`elasticsearch.yml` can be edited from a shell inside the node. The image holds
all six node configs; on a container's first start the entrypoint copies that
node's file to `config/elasticsearch.yml`. Config is not mounted from the host: edits live in the container's writable layer, survive
`./ece restart <node>`, and are discarded on reset (containers are recreated),
which is the desired behavior.

### Security

- Security enabled, TLS on HTTP and transport.
- A **single CA**, generated by the one-shot `certs` service into a named
  volume, signs the certificates of both clusters, so the clusters trust each
  other for cross-cluster operations. The CLI copies the CA to `.state/ca.crt`.
- Kibana is plain HTTP; it talks to its cluster over HTTPS using all three
  nodes as hosts, so it keeps working when one node is stopped.
- Both remote cluster security models work:
  - **Certificate-based**: over the transport port, using the shared CA.
  - **API key-based**: every node has the remote cluster server port (9443)
    enabled with TLS in its config, so tasks only need the APIs (cross-cluster
    API key, remote cluster settings). Requires the trial license.
- Security is already set up, so "secure a cluster from scratch" (enabling
  TLS, first-time passwords) is a reading item, not a hands-on task. Security
  tasks that work on a running cluster are hands-on: keystore, certutil,
  file-realm users, audit logging, password resets, roles, API keys.

### Licensing

Each cluster starts on a **30-day trial**
(`xpack.license.self_generated.type: trial` in the node configs). This enables trial-only features such as
cross-cluster replication and searchable snapshots. The trial is per cluster:
a full reset creates new clusters, which can start a new trial.
`./ece status` shows the days remaining. Taxonomy entries that need the trial
are tagged `license: trial`.

### Snapshot repositories

`fs` repositories require every node of a cluster to write to the **same
directory** (each node writes its own shards). Snapshots are never transferred
over the network between clusters; another cluster restores by registering the
same repository and reading the files.

One Docker named volume is mounted at `path.repo` in all six nodes, with
subdirectories:

- `a/`: cluster A's repositories
- `b/`: cluster B's repositories
- `shared/`: for tasks like "snapshot on A, restore on B"

### Data

**Kibana sample datasets** (web logs, eCommerce, flights), loaded into each
cluster through its own Kibana's sample data API during install. In 9.x this is
an internal Kibana API (needs the `x-elastic-internal-origin` header), and the
web logs dataset is a **data stream** (`kibana_sample_data_logs`), the other
two are plain indices. Tasks that
need specific data create it in their `setup()` step.

### Machine learning (semantic search)

`semantic_text` and the semantic query need an ML model. Elasticsearch 9.3 has a
preconfigured inference endpoint for ELSER (`.elser-2-elasticsearch`); its first
use downloads the model (~270 MB, needs internet) and deploys it with adaptive
allocations: about 2 GB of native memory while active, scaled down to zero when
idle (the first request after a quiet period takes a few seconds longer).
`./ece ml-setup` triggers this on both clusters and waits until ELSER answers.
Tasks that need it are tagged `requires: ml`; `./ece next` and `./ece selftest`
include them only when the model is available, and `./ece new` refuses them
with a hint until then. kNN and RRF tasks use precomputed vectors and need no
model.

### Host requirements and preflight

`install.sh` checks, before starting anything:

- Docker and Docker Compose v2 are installed and the daemon is running
- Python 3.10+
- Free ports (9200, 9201, 5601, 5602)
- Available memory
- `vm.max_map_count >= 262144`

#### vm.max_map_count

Elasticsearch memory-maps index files. Each mapping uses a kernel "map area";
Linux defaults to 65530 per process, and Elasticsearch requires 262144. With a
lower value, nodes fail their bootstrap checks and refuse to start. This is a
**host kernel** setting, so it cannot be set in docker-compose.

| Host | How to set it |
|---|---|
| Native Linux | `sysctl -w vm.max_map_count=262144`, persisted in `/etc/sysctl.d/` |
| WSL2 (Docker Engine in the distro, or Docker Desktop) | `%UserProfile%\.wslconfig` → `[wsl2]` `kernelCommandLine = sysctl.vm.max_map_count=262144`, then `wsl --shutdown` |
| macOS Docker Desktop | Usually already sufficient |

The installer detects a low value, offers to set it with sudo for the current
boot, and prints how to persist it for the detected platform.

#### Docker on WSL2

Recommended: **Docker Engine installed inside the WSL distro** (with systemd
enabled in `/etc/wsl.conf`) rather than Docker Desktop. It is lighter and has
no licensing questions. Docker Desktop also works.

## The `ece` CLI

A single Python 3 script using only the standard library (no pip, no venv).

```
./ece status                     # cluster health, URLs, password, trial days, active scenario
./ece list [--domain X] [--todo] # task templates, with progress
./ece new <template> [--seed N]  # generate a task instance (runs its setup)
./ece next                       # new task from a template not yet passed
./ece tasks                      # open task instances
./ece show <task-id>             # task prompt and the relevant doc links
./ece answer <task-id>           # write/edit the answer to a query task
./ece check <task-id>            # verify against the cluster, record the result
./ece solution <task-id>         # print the reference solution (Kibana console syntax)
./ece drop <task-id>             # remove a task and everything it created
./ece progress [--md]            # progress per taxonomy entry; optional Markdown checklist
./ece done <topic>               # tick off a reading item
./ece scenario list|start|check|explain|reset
./ece exam [start|finish|results|clean|abort]  # timed exam mode
./ece ml-setup                   # optional: download and deploy ELSER
./ece shell <node>               # shell into a node (e.g. a2)
./ece config <node>              # edit a node's elasticsearch.yml (also when it's stopped)
./ece restart|stop|start <node>  # node control
./ece reset                      # full wipe and rebuild
./ece selftest [--domain X]      # validate templates against a live cluster
./ece taxonomy [--tree] [--links] # validate the taxonomy and its doc links
```

## Task system

### Templates

Each template is a subclass of `Task` (`lib/tasklib.py`) in
`tasks/<domain>/<name>.py`, declaring:

- `id`: stable identifier starting with its domain, e.g. `ingest-weblog-pipeline`
- `covers`: taxonomy entry IDs it exercises, e.g. `["ingest.pipelines.processor.dissect"]`
- `params(rnd, iid)`: randomized values (thresholds, formats, categories, ...)
  from a seeded `random.Random`, so tasks can't be memorized
- `setup(ctx)`: creates whatever the task starts from
- `prompt(ctx)`: the task text, written in the style of the exam
- `solution(ctx)`: reference solution in Kibana console syntax, pasteable
  into Dev Tools
- `verify(ctx, c)` (state tasks): adds checks to a `Checker`; each check is
  printed with ✔/✘ and a reason
- `compare` or `grade(ctx, c, answer, reference)` (query tasks): how the
  user's response is compared with the reference's (`hits`, `hits_ordered`,
  `aggs`, `esql`, or custom)
- `wrong_answer(ctx)` (optional): a plausible wrong answer; selftest checks
  that it fails grading
- `apply_solution(ctx)` (optional): how selftest applies the solution; the
  default runs the console text on the task's cluster. Override it when the
  solution has steps that aren't API calls (node shell commands, keystore
  entries, values copied from one response into the next, both clusters)
- `cleanup(ctx)` (optional): removes what the generic cleanup doesn't know
  about (auto-follow patterns, remote cluster settings, API keys, keystore
  entries, files in node containers); runs on `drop` and after selftest
- `size`: `drill` (one feature) or `exam` (several features combined, like a
  real exam task, e.g. template + ILM + data stream + alias)
- `answer`: `state` (graded by inspecting the cluster) or `query` (graded by
  running the user's request, see below)
- optional `cluster`: which cluster(s) the task targets
- optional `requires`: `shell` (node-level access), `ml` (needs `./ece ml-setup`)

Prompts, solutions and verification are all rendered from the same parameters,
so the solution always matches the exact task instance.

Task style follows the exam: prose requirements with named resources, data
given inline or created by `setup()`, and often a chain of steps building on
each other (reindex → filtered reindex → pipeline on the result).

### Task instances

An instance gets a short random ID (e.g. `7a1f`) and records its template and
seed, so it is reproducible (`./ece new <template> --seed N`). Every resource
an instance creates carries its ID in the name (`products-7a1f`), so many tasks
can coexist in the clusters, and `./ece drop` can delete everything the task
created on both clusters. Commands that take a task ID default to the most
recent task. Sample data indices are shared and only read by tasks.

Resource names must not match Elasticsearch's built-in index templates, or
indices turn into data streams or get unexpected settings: avoid
`logs-*-*`, `metrics-*-*`, `traces-*-*`, `synthetics-*-*` and `profiling-*`
(e.g. use `applogs-7a1f-000001`, not `logs-7a1f-000001`).

### Verification

Grading inspects end state, not the commands used:

- **State tasks** (mappings, templates, ILM, roles, settings): read the
  resource and compare the relevant parts.
- **Ingest pipelines**: run `_ingest/pipeline/<id>/_simulate` with known input
  and compare the output.
- **Data tasks** (reindex, update by query): document counts and samples.
- **Security**: create a temporary user with the role and test what it can
  and cannot do.
- **Query tasks** (Query DSL, aggregations, ES|QL, async search, runtime
  fields in the request, highlighting, sorting, pagination, CCS, kNN,
  semantic search): the checker runs the user's answer and the reference
  solution and compares the results (hits, order where the task requires it,
  aggregation values, ES|QL rows), not the request text.

### Writing templates

Lessons from the first batch, checked for every new template:

- **Sample data values** come from `lib/sampledata.py` (index names, categories,
  carriers, ...), so randomized values always match a sensible number of documents.
- **Every variant must be meaningful.** `./ece selftest --sweep N` runs each query
  task's reference for N random variants and reports empty results, and truncated
  results for "return all matches" tasks. Thresholds are chosen from the actual
  data distribution so that every combination gives a different, non-empty result.
- **`wrong_answer()` must be reliably wrong**, not just plausibly wrong: an answer
  that only differs for some variants passes by luck (e.g. ordering by count can
  coincide with ordering by revenue). Selftest catches these.
- **Scoring tasks compare scores** (`compare = "hits_scored"`, with a small
  tolerance), since the same top order can come from different formulas.
  Equivalent query forms (multi_match vs bool/should) give the same scores.
- **Prompt and solution must agree** on everything graded (column order, bucket
  names, which hits). Selftest compares the solution with itself, so this needs a
  read-through: render all prompts and solutions and read them side by side.
- **Range buckets** are compared by their bounds, so user-chosen band names don't
  matter; filter buckets have no bounds, so the prompt names them.
- **Python 3.10**: no nested same-type quotes in f-strings (3.12 only).
- **Keystore entries must never block a node from starting.** An incomplete
  secure setting group (e.g. an S3 client with a secret key but no access key)
  makes the node refuse to boot on its next restart. Tasks only ever add or
  remove complete groups, and their `cleanup()` removes every entry with the iid.
- **Node-level tasks** (static settings, node roles, restarts) use `lib/nodes.py`:
  `set_settings()`, `restart()` (waits until the node has rejoined) and
  `restore()`, which puts the lab's original config back (every container
  holds the originals from the image). Their `cleanup()` always calls
  `restore()`, so an abandoned task never leaves a modified node behind.
- **Helpers** shared by a domain's templates live in `tasks/<domain>/_*.py`
  (the loader skips files starting with `_`). A template file that fails to
  load is skipped and reported by `./ece list` and `./ece selftest`, so one
  broken file never breaks the CLI.

### Answers to query tasks

The user writes the request in Dev Tools, then hands it to the CLI in Kibana
console format, exactly as it appears in Dev Tools (`GET index/_search` plus
the JSON body; `"""` strings for ES|QL work too):

- `./ece answer <task-id>` opens the answer in vim (or `$EDITOR`); the file
  starts with the task's prompt as comments.
- `./ece answer <task-id> --paste` reads it from the terminal instead (paste,
  then Ctrl-D).
- `./ece check <task-id>` on a query task without an answer offers to open the
  editor first.

Answers are stored in `.state/answers/<task-id>.txt`. An answer can hold
several requests (e.g. submit an async search, then fetch it); the last
response is graded.

### Taxonomy

- `taxonomy/` describes the curriculum as a tree: domain → topic → feature
  (e.g. `search.query.fulltext.match_phrase`). It is derived from the exam
  topics document (`elastic_docs_links.md`), and each entry carries the doc
  links for it. `./ece show` prints them with the task, since the docs are the
  only reference allowed in the exam and finding pages fast is a skill.
- Entries are `hands-on` (practised through tasks) or `reading` (conceptual, e.g. stack
  architecture or shard sizing guidance; ticked off with `./ece done`).
- Each entry has a level: `core` (marked core in the topics document, or a
  staple of exam tasks), `common` (named in the topics document or a
  must-know reference item) or `extended` (the rest of the reference, e.g.
  rare token filters, span queries, exotic aggregations). Each entry can also
  carry requirements: `shell`, `ml`, `kibana`, `cluster-b`.
- The data is Python (`taxonomy/<domain>.py`, built with helpers from
  `lib/taxonomy.py`), so long reference lists such as processors or
  aggregations are compact tables. The lists were checked against 9.3.8:
  processors against `GET _nodes/ingest`, ES|QL commands against the
  parser, query, aggregation and field types by trying them on the cluster.
- `./ece taxonomy` validates the data and prints counts; `--tree` prints every
  entry; `--links` checks every doc link against elastic.co.
- `./ece selftest` runs, for every template: generate an instance, confirm
  `verify` **fails**, apply the reference solution, confirm `verify` **passes**.
  It is run locally after changing templates (no CI).

### Progress tracking

`./ece check` records results in `.state/`. `./ece progress` rolls them up by
taxonomy entry (not started / attempted / passed) with a percentage per
domain, counting only entries that have at least one task, plus the reading
items. Entries without tasks yet are listed separately as "no tasks yet".
`--md` writes a Markdown checklist.

## Troubleshooting scenarios

Each scenario is a subclass of `Scenario` (`lib/scenariolib.py`) in
`scenarios/<name>.py`, with:

- `params(rnd, iid)`: picks a variant (several causes per scenario)
- `cause()`: puts a cluster into a broken state
- `brief()`: the symptom and the **required outcome**, never the cause
- `verify()`: checks the outcome, not the steps taken
- `explain()`: the cause, how to find it, and the fix, shown on request
- `fix()`: the reference fix in console syntax; `apply_fix()` applies it in
  selftest (overridden when the fix isn't only API calls, e.g. starting a node)
- `reset()`: undoes the scenario, including any cluster settings it changed

Briefs state the required end state the way an exam task would, e.g. "Cluster A
is yellow. Fix it so that the cluster is green again, and every index keeps its
current number of replicas and all of its documents." Workarounds that break
the stated outcome (dropping replicas, deleting data) fail; any fix that reaches
it passes. Only one scenario is active at a time; `./ece status` shows which.

| Scenario | Variants of the cause |
|---|---|
| `yellow-index-allocation-filter` | index-level require/include filter leaving one node |
| `yellow-cluster-allocation-filter` | cluster-level exclude by name, zone or temp |
| `allocation-disabled` | `cluster.routing.allocation.enable`: none, primaries, new_primaries |
| `allocation-awareness` | awareness on a missing attribute (red), forced awareness on a missing value (yellow) |
| `yellow-too-many-replicas` | more replicas than nodes allow |
| `yellow-total-shards-per-node` | per-index shard limit too low |
| `cluster-shard-limit` | `cluster.max_shards_per_node` below the open shards |
| `disk-flood-stage` | watermarks below disk usage, read-only blocks |
| `red-lost-node` | a stopped node held the only copy of an index |
| `ilm-rollover-error` | missing alias, wrong rollover_alias, alias not write index |
| `remote-cluster-unreachable` | wrong port, wrong host, proxy mode on the HTTP port |
| `user-cannot-search` | wrong index pattern, wrong privilege, misspelled role |
| `node-config-error` | missing certificate, misspelled setting, broken YAML, wrong cluster name |

`node-config-error` breaks a node's elasticsearch.yml (missing certificate,
misspelled setting, broken YAML, wrong cluster name). A stopped container
can't be shelled into, so `./ece config <node>` edits the file with
`docker cp` instead, which works whether the node runs or not.

The intended workflow is to diagnose with `_cluster/health`, `_cat/shards`,
`_cluster/allocation/explain`, `_health_report`, `_ilm/explain` and so on,
without reading the scenario source.

## Reset

- `./ece reset`: `docker compose down -v`, then re-run initialization.
  Everything is fresh: certificates, clusters, data, node configs, and trial.
  Takes about 3 minutes, mostly Kibana startup.
- `./ece scenario reset`: undoes only the active scenario.

Progress in `.state/` is never touched by a reset; open tasks and the active
scenario are forgotten, since their resources are gone. `ECE_STATE_DIR`
points the CLI at another state directory (used for testing without touching
real progress).

## Exam mode

The real exam is about 10 weighted tasks in 3 hours. `./ece exam start`
(`lib/exam.py`) picks 10 tasks: exam-size tasks first (at most half, one per
domain), then core drills round-robin over the domains, and starts a 3-hour
timer (`--count`, `--minutes` change both). During the exam:

- `./ece exam` lists the tasks and the time left; `./ece show` prints a task
  without doc links (finding the docs is part of the exam).
- `./ece check` and `./ece solution` are refused, and `drop` too (`./ece exam
  abort` cancels the whole exam); answers can be handed in until the time is up.
- `./ece exam finish` grades everything at once: each task passes only if all
  its checks pass, exam-size tasks weigh 2 and drills 1, and the score is the
  percentage of points. Results go into progress; solutions unlock.
- `./ece exam results` shows the last score again, `./ece exam clean` removes
  the finished exam's tasks.

`./ece status` shows a running exam and its time left.

## Spoilers

Task and scenario sources contain solutions. The README warns users not to
read `tasks/` and `scenarios/` if they want to avoid spoilers; the CLI is the
intended interface.

## Build order

1. Infrastructure: compose (2 clusters, 2 Kibanas, TLS, shared snapshot
   volume, vim image), `install.sh` with preflight, trial license, sample data,
   reset, uninstall.
2. Taxonomy from the topics document: the full list of features and reading
   items, each with its doc links. This defines the task catalog.
3. CLI and template format, proven end to end with a few templates of
   different kinds (state, pipeline simulation, query answer) and one
   scenario; progress tracking.
4. Troubleshooting scenarios.
5. Filling the task catalog domain by domain, with selftest.
6. `ml-setup`, exam mode.
